# Time-Series Foundation Models and LLM Agents for Research Vessel Underway Data (OpenRVDAS context)

Scope note: Research done 2026-11-17. Every URL below was opened during research unless it appears only in Gaps. Vendor and author self-reported numbers are labeled as such. "Proven" means demonstrated in a peer-reviewed or primary-source evaluation; "speculative" means my inference for shipboard use, with no deployed evidence found.

## Q1. Time-series foundation models (TSFMs): what exists, sizes, licenses, CPU feasibility, benchmarks, and honest critiques

### Takeaway
TSFMs are now real, small (under 1M to about 200M params), mostly Apache-2.0, and genuinely good at zero-shot univariate forecasting on curated benchmarks, but benchmark wins have shrinking margins, leakage is a known issue, they lag at high (second/minute) frequency which is exactly what underway data is, and for anomaly detection a 2026 ICLR paper finds they do not beat one-line baselines (rolling variance, squared difference). For an RV, the defensible near-term uses are (1) gap-filling/imputation and short-horizon "expected value" bands as a secondary QC signal, and (2) covariate-aware forecasting (Chronos-2), all run on CPU with small models, never as the primary QC flagger.

### Cited Findings

Model facts (sizes, licenses, capabilities)
- Chronos-2 (Amazon, Oct 2025): base model 120M parameters; supports univariate, multivariate, past-only covariates, known covariates, categorical covariates and cross-learning (in-context learning across series); throughput about 300 series/s on one A10G GPU for batch 1,024, context 2048, horizon 64. Training data includes selected Chronos and GIFT-Eval pretraining datasets plus synthetic data. — [Chronos-2 paper, arXiv 2510.15821](https://arxiv.org/html/2510.15821v1)
- Chronos-Bolt: Tiny 9M, Mini 21M, Small 48M, Base 205M params; Apache-2.0; vendor claims "up to 250 times faster" and "20 times more memory-efficient" than original Chronos of same size; inference example lists "cpu" and "mps" devices; SageMaker endpoints run on CPU or GPU instances. — [HF model card amazon/chronos-bolt-small](https://huggingface.co/amazon/chronos-bolt-small)
- TimesFM 2.5 (Google, released 2025-09-15): 200M params (down from 500M in 2.0), context up to 16k (up from 2,048), optional 30M quantile head for horizons up to 1k, frequency indicator removed; covariate support via XReg added back 2025-10-29; code and weights up to 2.5 are Apache-2.0. — [google-research/timesfm GitHub](https://github.com/google-research/timesfm)
- TimesFM 3.0 (Aug 2026) weights are under a separate "timesfm-non-commercial-license-v1.0" restricting use to non-commercial, non-production purposes; commercial use via Google Cloud (BigQuery ML). Google claims 3.0 is #1 among foundation models on GIFT-Eval and #1 on fev-bench and TIME (self-reported). — [google-research/timesfm GitHub](https://github.com/google-research/timesfm)
- TimesFM 2.5 is in Hugging Face Transformers (contributed 2026-02-27): defaults 20 layers, hidden 1280, context 16384, horizon 128, nine quantiles; `infer_is_positive` clamps forecasts to non-negative when input is non-negative (a gotcha for signed variables like heave or temperature anomalies near zero); univariate `past_values` input in the Transformers implementation. — [HF Transformers TimesFM 2.5 docs](https://huggingface.co/docs/transformers/model_doc/timesfm2_5)
- Moirai 2.0 (Salesforce, Nov 2025): decoder-only, quantile loss, single patch size; "thirty times smaller" than Moirai 1.0-Large and twice as fast while better; ranked 5th of 37 foundation models on GIFT-Eval at publication; univariate only (multivariate treated as independent series); performance plateaus with size and declines at longer horizons; part of pretraining is internal Salesforce telemetry. KV-cache gives up to 4x speedup for ~10K context. Exact param counts and weights license not stated on the page opened. — [Moirai 2.0 paper, arXiv 2511.11698v3](https://arxiv.org/html/2511.11698v3)
- IBM Granite TTM-R2: 805k params (card says sizes "start from 1M"), Apache-2.0, runs on "CPU-only machines" and laptops; context 512/1024/1536 variants; supports channel-independent and channel-mixing, exogenous infusion; r2 covers minutely to hourly resolution (r2.1 adds daily/weekly); point forecasts; competitive fine-tuning with about 5% of training data; IBM says it is an open-source project, not a product, with no maintenance commitment. — [HF model card ibm-granite/granite-timeseries-ttm-r2](https://huggingface.co/ibm-granite/granite-timeseries-ttm-r2)
- Toto (Datadog): 151M params; weights, inference code, eval scripts Apache-2.0; trained on about 2.36T points, 43% anonymous Datadog observability metrics; context 4096, patch 64; strong multivariate inference speed (>30 variates). BOOM benchmark: about 350M points, 2,807 metric queries, 32,887 variates, all real observability data. Toto BOOM MASE 0.617, CRPS 0.375 (authors report about 12% CRPS better than next best); GIFT-Eval MASE 0.673, CRPS 0.437 as of May 2025. — [Toto/BOOM paper, arXiv 2505.14766v2](https://arxiv.org/html/2505.14766v2)
- MOMENT (CMU AutonLab): Small ~40M, Base ~125M, Large ~385M; tasks: long/short-horizon forecasting, classification, anomaly detection, imputation; fixed 512 input length, channel-independent; per-signal normalization means it cannot distinguish vertically shifted series (important for sensor offset/drift detection); short-horizon zero-shot forecasting is its weakest area, where Theta and ETS often beat it; training footprint about 72 tCO2eq. — [MOMENT paper, arXiv 2402.03885v3](https://arxiv.org/html/2402.03885v3)
- MOMENT anomaly detection on UCR Anomaly Archive: adjusted best F1 MOMENT-LP 0.628, zero-shot 0.585, k-NN 0.554; but on VUS-ROC simple k-NN scored highest (0.706) vs MOMENT-LP 0.684. Imputation: MOMENT-LP best on ETT datasets (ETTh1 MSE 0.139 vs TimesNet 0.175), but GPT4TS better on Weather (0.031 vs 0.035); zero-shot MOMENT beat statistical interpolation methods except linear interpolation. — [MOMENT paper](https://arxiv.org/html/2402.03885v3)

Benchmarks
- fev-bench (Sep 2025): 100 tasks, seven domains, 46 with covariates; bootstrapped confidence intervals, win rates and skill scores; critiques prior benchmarks for weak statistical rigor and ignoring covariates. — [fev-bench, arXiv 2509.26468](https://arxiv.org/abs/2509.26468v2)
- fev-bench results as reported in the Chronos-2 paper (authors are Chronos-2's developers, so treat as interested-party): win rate / skill score / median runtime / leakage: Chronos-2 90.7% / 47.3% / 3.6 s / 0%; TiRex 80.8% / 42.6% / 1.4 s / 1%; TimesFM-2.5 75.9% / 42.3% / 16.9 s / 8%; Toto-1.0 66.6% / 40.7% / 90.7 s / 8%; Moirai-2.0 61.1% / 39.3% / 2.5 s / 28%; Chronos-Bolt 60.3% / 38.9% / 1.0 s / 0%; TabPFN-TS 59.3% / 39.6% / 305.5 s / 0%; Sundial 41.0% / 33.4% / 35.6 s / 1%. Chronos-2 is the only one in that table with full covariate + multivariate support; Chronos-Bolt, Moirai-2.0, Sundial, TimesFM-2.5 and TiRex are univariate. — [Chronos-2 paper](https://arxiv.org/html/2510.15821v1)
- Note the skill-score spread between the top model and the fast small Chronos-Bolt is about 8 points (47.3 vs 38.9), while runtime differs 3.6x. — [Chronos-2 paper](https://arxiv.org/html/2510.15821v1)
- GIFT-Eval: 23 datasets, ~144k series, 7 domains incl. "Nature" (weather), 10 frequencies from secondly to yearly; non-leaking pretraining set ~230B points. Original findings: foundation models lag most at secondly and minutely frequency (Auto_Theta wins secondly; iTransformer/PatchTST/TFT win minutely/hourly); TimesFM and Chronos decline at medium/long horizons; deep models (PatchTST) lead multivariate; scaling law holds only in some cases. These findings are for the late-2024 model generation. — [GIFT-Eval paper, arXiv 2410.10393](https://arxiv.org/pdf/2410.10393)
- Leakage: Moirai 2.0 states it trains only on the non-leaking GIFT-Eval pretrain split and compares only to models without test leakage — [Moirai 2.0](https://arxiv.org/html/2511.11698v3); Toto's authors note several competing models have known partial leakage with GIFT-Eval — [Toto paper](https://arxiv.org/html/2505.14766v2); fev-bench as tabulated by Chronos-2 shows leakage up to 28% for Moirai-2.0 and 8% for TimesFM-2.5 and Toto, with leaky tasks imputed — [Chronos-2 paper](https://arxiv.org/html/2510.15821v1).

Critiques
- Tan et al. (NeurIPS 2024 Spotlight): in three popular LLM-based forecasting methods, removing the LLM or replacing it with a basic attention layer did not degrade and often improved performance; pretrained LLMs did no better than training from scratch, did not capture sequential dependencies, and did not help few-shot. Note this critique targets repurposed text LLMs (e.g., Time-LLM style), not natively trained TSFMs like Chronos/TimesFM. — [arXiv 2406.16964](https://arxiv.org/abs/2406.16964)
- "When Foundation Models are One-Liners" (ICLR 2026): tested MOMENT, Chronos, TimesFM, Time-MoE and TSPulse across sizes and context lengths; anomaly detection did not meaningfully beat moving-window variance and squared-difference one-liners; anomalies are not consistently harder to forecast or reconstruct, so the residual-based AD assumption does not hold. — [ICLR 2026 poster page](https://iclr.cc/virtual/2026/poster/10010437)

### Inferences
- Underway data (1 Hz to 1 min, e.g., TSG, met, fluorometer, gravimeter, ADCP ensembles) sits exactly in the second/minute regime where GIFT-Eval found TSFMs weakest. Expect a classical baseline (ETS/Theta, seasonal naive, or a rolling median plus MAD) to be competitive; any TSFM deployment should be A/B tested against these on ship data.
- Forecast-residual anomaly detection with TSFMs should not be the primary QC mechanism given the ICLR 2026 one-liner result. Classical range/gross/spike/stuck/rate-of-change tests (QARTOD-style) remain the baseline; a TSFM residual can be an extra, explainable "this deviates from expected" signal.
- Covariate-aware models (Chronos-2, TimesFM 2.5 XReg, TTM exogenous) are the interesting ones for ships: e.g., predict TSG temperature from intake temperature plus ship speed/heading, or cross-check redundant sensors. A large residual between redundant sensors is physically meaningful in a way a univariate forecast residual is not.
- CPU feasibility: TTM (805k) and Chronos-Bolt Tiny/Mini/Small (9M to 48M) are clearly CPU-scale; 120M to 205M models (Chronos-2, TimesFM 2.5, Bolt Base) are likely fine on a shipboard server CPU for batch/minute-scale jobs but not proven here for latency. No source opened gave CPU benchmarks.
- Imputation is a plausible near-term win (short gaps from serial dropouts), but MOMENT's own results show linear interpolation is a strong baseline; for short gaps, interpolation probably suffices and is more defensible for archival data. TSFM-imputed values must be flagged as synthetic and never overwrite raw data.
- Licensing trap: TimesFM 3.0 is non-commercial; for a UNOLS operator or a vendor shipping OpenRVDAS add-ons, stick to Apache-2.0 models (Chronos-2/Bolt, TimesFM 2.5, TTM, Toto) after verifying each card.

### Gaps
- Not opened (no verified facts): Lag-Llama, Timer / Timer-XL, Sundial (beyond fev-bench row), TabPFN-TS (beyond fev-bench row), TiRex, Moirai-MoE, Moirai 1.x licenses (Moirai 1.x weights were historically CC BY-NC, unverified here), Chronos-2 weights license (likely Apache-2.0, not confirmed on opened page), Monash archive results.
- No published CPU latency benchmarks found for Chronos-2 or TimesFM 2.5.
- No published application of any TSFM to research vessel underway data found. Ocean/environmental TSFM applications were not specifically located within the search budget.
- Current GIFT-Eval leaderboard standings (late 2026) not opened directly; only self-reported claims (TimesFM 3.0 #1).

## Q2. Earth/ocean foundation models (weather and ocean AI) as context/forecast references for a ship

### Takeaway
Gridded AI weather and ocean models are operational or near-operational and cheap to run once trained, and ECMWF's AIFS now issues open (CC BY 4.0) data-driven wave and atmosphere forecasts. A ship would almost always consume their products (downloaded fields) rather than run them, and the best fit is as "expected background" for comparing underway met/SST/wave observations and for planning, not for real-time QC of point sensors.

### Cited Findings
- ECMWF AIFS Single v2: operational since 2026-05-12, 15-day 6-hourly global forecasts four times daily, ~31 km, 14 pressure levels; weights CC BY 4.0, scripts Apache-2.0; checkpoint ~994 MB; trained on 16 GH200 GPUs; needs initial conditions (t-6h and t0) from ECMWF Open Data; includes 11 wave variables (significant wave height, mean period/direction, banded Hs) described as ECMWF's first operational data-driven wave forecasts, plus SST. Inference hardware requirements not stated. — [HF ecmwf/aifs-single](https://huggingface.co/ecmwf/aifs-single)
- Microsoft Aurora (Nature 2025): trained on >1 million hours of diverse Earth data; fine-tuned for ocean wave height/direction, air quality, tropical cyclone tracks (reported to beat NHC on 5-day tracks), 0.25 degree medium-range weather; forecasts in seconds, claimed ~5,000x faster than traditional systems; source code and weights public. Secondary press source. — [HPCwire summary](https://www.hpcwire.com/aiwire/2025/05/21/microsofts-aurora-ai-foundation-model-goes-beyond-weather-forecasting/); Nature citation record — [IDEAS/RePEc](https://ideas.repec.org/a/nat/nature/v641y2025i8065d10.1038_s41586-025-09005-y.html)
- XiHe ocean model: 1/12 degree eddy-resolving, trained on 25 years of GLORYS12; predicts temperature, salinity, zonal/meridional currents on 23 depth layers and SSH, using OSTIA SST and ERA5 10 m winds as inputs; 10-day forecast in 0.35 s on one GPU; authors claim it beats PSY4, GIOPS, BLUElink, FOAM (e.g., 10-day current errors 10 to 11% lower than PSY4). Weights availability not stated. — [XiHe, arXiv 2402.02995v4](https://arxiv.org/html/2402.02995v4)

### Inferences
- Shipboard use pattern (speculative but low-risk): pull AIFS open-data fields (or Copernicus/NOAA products) when bandwidth allows, interpolate to the ship track, and store as a "model-expected" channel alongside observed met/SST/Hs. Divergence flags either a sensor problem or a real feature (front, eddy), which is useful context for both QC and science.
- Running these models aboard is generally unnecessary: they need global initial conditions that come from shore, so the bandwidth cost is the same as downloading the forecast product. Inference on a ship CPU is not documented.
- Validation direction is reversed too: underway observations are valuable independent verification for these AI models, a possible science-community contribution.

### Gaps
- Not opened: GraphCast, FourCastNet, NVIDIA Earth-2, Prithvi (NASA/IBM), WenHai, ORCA ocean models. No license/compute facts for those are included here.
- No example found of a research vessel ingesting AI weather/ocean model output into its data acquisition system.

## Q3. LLM agents for data analysis: accuracy evidence, failure modes, guardrails

### Takeaway
On realistic benchmarks, LLM agents remain far from expert level: about one-third accuracy on DSBench analysis tasks (GPT-4o era) versus 64% for humans, and roughly 20 to 27% execution accuracy on enterprise Spider 2.0 text-to-SQL at release. BLADE shows agents default to basic analyses. Newer models have improved but the pattern holds: agents are useful when grounded in tools with verifiable outputs and fixed pipelines, and risky when trusted for open-ended statistical conclusions.

### Cited Findings
- DSBench: 466 data analysis tasks (ModelOff) and 74 modeling tasks (Kaggle). Best agent (AutoGen + GPT-4o) solved 34.12% of analysis tasks; human baseline 64.06%. Accuracy drops with longer inputs, multi-table reasoning and harder/newer tasks (66.67% on 2012 competitions vs 13.01% on 2017). Higher task-completion rate did not imply better solutions. — [DSBench, arXiv 2409.07703v3](https://arxiv.org/html/2409.07703v3)
- Spider 2.0 (enterprise text-to-SQL, Snowflake variant): ReFoRCE (o1-preview) 26.69% EX, Spider-Agent (o1-preview) 20.29%, DAIL-SQL (GPT-4o) 2.20%, DIN-SQL (GPT-4o) 0.00%, vs >90% on Spider 1.0. An aggregator cites ~80% EX on English Spider 2.0 from a later paper; this conflicts with the leaderboard numbers and is unresolved. — [Emergent Mind topic page, Spider 2.0](https://www.emergentmind.com/topics/spider-2-0-benchmark)
- BLADE: 12 datasets with research questions from published literature, expert analyses as ground truth; LM agents are "often limited to basic analyses"; agents that interact with data show "improved, but still non-optimal, diversity in their analytical decision making." — [BLADE, arXiv 2408.09667](https://arxiv.org/abs/2408.09667)
- OceanAI (NC State with NOAA co-authors, Nov 2025): LLaMA-based coordinating agent with a fixed pipeline; function calling to parameterized NOAA dataset functions (CO-OPS tides, CORA reanalysis, Coral Reef Watch SST); every function returns text, images, JSON data and metadata (source, units, location, time range); RAG over 235 papers and 23 NOAA tech reports. On 7 structured-data prompts, OceanAI was correct on all while ChatGPT, Gemini and Grok failed all 7. Evaluation is only 14 pass/fail prompts; no hallucination rate measured. — [OceanAI, arXiv 2511.01019v2](https://arxiv.org/html/2511.01019v2)
- OceanGPT (ACL 2024): ocean-domain LLM trained with auto-generated instruction data (DoInstruct); introduces OceanBench. Abstract page gives no size or results. — [ACL Anthology 2024.acl-long.184](https://aclanthology.org/2024.acl-long.184)

### Inferences
- The OceanAI result is the most relevant evidence pattern: ungrounded chat LLMs fail on structured, live ocean data; grounding via typed tool calls with provenance metadata fixes the specific failure (with a tiny eval). This directly supports the OpenRVDAS MCP design: every MCP tool response should carry source logger, sensor, units, time window, QC flags and a query echo.
- Guardrails implied by the evidence: (a) all numbers computed by tools (SQL/pandas executed against the cache or DB), never by the LLM; (b) the generated query/code is shown and logged (notebook-style), so results are reproducible; (c) restrict open-ended "is this significant?" analysis, given BLADE/DSBench; (d) human sign-off on anything entering cruise reports or archives; (e) prefer a narrow, curated query API over free text-to-SQL, given Spider 2.0 accuracy on messy schemas.
- Failure modes to expect on ships: wrong units/time zones (UTC vs ship time), mixing raw and corrected channels, confident summaries of data with dropouts, and hallucinated sensor names. Typed MCP tools with enumerated channels mitigate the last.

### Gaps
- Not opened: DA-Code, InfiAgent-DABench, DiscoveryBench, BIRD leaderboard, Google AI co-scientist, data-to-paper, ChatClimate, ClimSight, MCP specification/security literature. No numbers for these are included.
- No 2026 frontier-model scores on DSBench or Spider 2.0 were verified; the numbers above are 2024 to 2025 era and likely understate current models.
- No evidence found quantifying p-hacking or hallucinated statistics rates for LLM agents in environmental data specifically.

## Q4. Concrete high-value LLM uses on ships and deployed examples (NOAA, Schmidt Ocean, OOI, MBARI, UNOLS)

### Takeaway
I found one real research-vessel-community LLM effort (a WHOI custom GPT "Shipboard Data Mate" presented at UNOLS RVTEC, Oct 2025) and one NOAA-linked grounded ocean-data chatbot (OceanAI), neither with published shipboard performance results. Everything else is proposed. The highest-value, lowest-risk uses are text-generation tasks over tool-computed facts: daily QC summaries, alarm explanations, OpenRVDAS YAML drafting with schema validation, and log troubleshooting.

### Cited Findings
- UNOLS RVTEC 2025 talk "Practical AI/ML Tools and Techniques for Shipboard Operations" (R. Mishra, 26 Oct 2025): "Shipboard Data Mate," a custom GPT for technicians on academic research vessels, aimed at CTD, ADCP and underway data: NetCDF handling, QA/QC script generation (Python/MATLAB/R), visualization, metadata, cruise reports and troubleshooting. Proposed use cases: run a NetCDF QC script, find LTER cruises with CTD data, draft an NCEI submission checklist, prepare a Zenodo data package. Constraints: 512 MB upload cap, no direct URL reading, message caps, WHOI-tenant access only. No results, no OpenRVDAS mention, no bandwidth/onboard compute discussion. Also lists non-LLM ML ideas (underwater radiated noise regression, power consumption NN, scheduling RL, corrosion image classification). — [UNOLS RVTEC 2025 slides (PDF)](https://www.unols.org/sites/default/files/2025-12/202511rvtec_mishra_rajesh_ai_ml_shipboard_ops.pdf)
- OceanAI is deployed as a web app on AWS EC2 (Next.js/Flask/ChromaDB), not at sea; it targets near-real-time NOAA coastal data. — [OceanAI paper](https://arxiv.org/html/2511.01019v2)

### Inferences (speculative, ranked by value-to-risk)
1. End-of-day / end-of-cruise QC report: tools compute uptime per logger, gap lists, flag counts, sensor-vs-sensor offsets, TSFM/classical residual outliers; LLM writes the narrative. Low risk because every number is tool-sourced and reviewable.
2. Alarm explanation: when an OpenRVDAS derived value or limit alarm fires, the LLM pulls the last N minutes of the channel and related channels and drafts "likely causes" (e.g., TSG flow drop coinciding with temperature spike suggests intake issue). Advisory only.
3. OpenRVDAS YAML config generation: draft logger/reader/transform/writer configs from a natural-language description or device manual, then validate by loading with OpenRVDAS's own config parser in a dry run. High value for techs, verifiable by machine.
4. Natural-language queries for science party/bridge ("SST and salinity at the last CTD station"): via a narrow MCP tool set rather than free SQL, given Spider 2.0 accuracy.
5. Log/troubleshooting assistant: summarize logger error logs, serial timeouts, NMEA checksum failures.
6. Cruise report drafting from event logs and QC summaries, with mandatory human edit.
- Deployment constraints: limited and expensive satellite bandwidth argues for a small local LLM for routine summaries with optional shore-side frontier model when connected; TSFMs at CPU scale (TTM, Chronos-Bolt) fit onboard. Not evidenced by any source here; design inference.
- Integration sketch for OpenRVDAS MCP (speculative): MCP tools `list_channels`, `get_series(channel, t0, t1, qc)`, `run_qc(channel, tests)`, `forecast_band(channel, covariates, model)`, `validate_config(yaml)`; each returns data plus provenance (logger, units, UTC window, code version) and is logged so any LLM statement can be traced to a tool call.

### Gaps
- No published LLM or TSFM deployment at sea found for Schmidt Ocean Institute, NOAA fleet, OOI or MBARI within the search budget (absence of evidence, not evidence of absence).
- No measured results for Shipboard Data Mate.
- No source on onboard LLM hardware or bandwidth economics for RVs.
