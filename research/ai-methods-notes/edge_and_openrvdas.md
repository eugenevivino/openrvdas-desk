## Q1. OpenRVDAS architecture as it exists now, and where QC / anomaly / drift detection should live

### Takeaway
OpenRVDAS is a Python framework of Readers -> Transforms (serial) -> Writers (parallel), wired by YAML and run by a logger manager; it already has a "derived data" pattern (TrueWindsTransform reading from the CachedDataServer and writing back to it) that is the natural template for a QC/anomaly logger, but its only built-in QC transforms (`QCFilterTransform`, `ValueFilterTransform`) are simple bounds checks, and `ValueFilterTransform` deletes out-of-range fields rather than flagging them. The recommended placement is a tiered one: cheap QARTOD-style flags as a separate "derived" logger subscribed to the CachedDataServer (never inline in the raw-logging logger), heavier windowed methods in a separate process/consumer, and change-point and reprocessing post hoc on stored data.

### Cited Findings

Core pipeline
- `Listener` "takes a list of one or more Readers, a list of zero or more Transforms, and a list of zero or more Writers. It calls the Readers (in parallel) to acquire records, passes those records through the Transforms (in series), and sends the resulting records to the Writers (in parallel)." Internally it builds `ComposedReader(readers=...)` and `ComposedWriter(transforms=..., writers=...)` and loops `record = self.reader.read(); self.writer.write(record)` with an optional `interval` sleep. — [logger/listener/listener.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/listener/listener.py)
- `ComposedWriter` applies transforms in series then writes to each writer in its own thread; the docstring warns "we make the rash assumption that transforms are thread-safe ... To be thread-safe, a transform must protect any changes to its internal state with a non-re-entrant thread lock", while writers get a per-writer lock to prevent re-entry. — [logger/writers/composed_writer.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/writers/composed_writer.py); same thread-safety note in [logger/transforms/README](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/README)
- Current reader modules: cached_data, composed, database, http, logfile, modbus, modbus_serial, mqtt, network, polled_serial, redis, sealog, serial, socket, tcp, text_file, timeout, udp, websocket. — [logger/readers/](https://github.com/OceanDataTools/openrvdas/tree/master/logger/readers)
- Current writer modules include cached_data, database, email, file, google_sheets, grafana_live, influxdb, logfile, logger_manager, mqtt, network, record_screen, redis, regex_logfile, sealog, serial, socket, tcp, text_file, timeout, udp, websocket. — [logger/writers/](https://github.com/OceanDataTools/openrvdas/tree/master/logger/writers)
- Current transform modules include computed_fields, convert_fields, count, delta, derived_data, extract_field, format, from_json, geofence, interpolation, max_min, modify_value, nmea_checksum, nmea, parse_nmea, parse, prefix, qc_filter, regex_filter, regex_parse, regex_replace, select_fields, slice, split, strip, subsample, timestamp, to_das_record, to_json, true_winds, unique, value_filter, xml_aggregator. — [logger/transforms/](https://github.com/OceanDataTools/openrvdas/tree/master/logger/transforms)
- Base class: `class Transform(BaseModule)`; the parent class now mainly provides optional type checking driven by the type hints on the child's `transform()` method (e.g. `def transform(self, record: Union[DASRecord, dict])`), with `can_process_record()` / `digest_record()` inherited helpers for lists and unexpected types. — [logger/transforms/transform.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/transform.py)
- `DerivedDataTransform` is now a "Trivial base class for derived data transforms. Derived data transforms used to have some complicated invocation process ... but we've opted to make them just like any other transform for simplicity." — [logger/transforms/derived_data_transform.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/derived_data_transform.py)

Existing QC transforms
- `QCFilterTransform(bounds, message=None)`: bounds are `field:lower:upper` triples; `transform()` "returns None unless values in passed DASRecord are out of bounds, in which case return a warning message" (a string). Docstring: "this module is due to be replaced by a more general value matching transform, as per GitHub feature request ... issues/406". — [logger/transforms/qc_filter_transform.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/qc_filter_transform.py)
- `ValueFilterTransform(bounds, log_level=logging.INFO)`: "filters out values in a passed DASRecord that are out of bounds"; the code does `del fields[bound]` for non-numeric or out-of-range values and logs at the configured level. — [logger/transforms/value_filter_transform.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/value_filter_transform.py)
- Other near-QC building blocks: `ComputedFieldsTransform(DerivedDataTransform)` evaluates equations with a restricted safe-function sandbox and is designed to be subclassed to add functions (docstring example `GSWComputedFieldsTransform`); also `delta_transform.py`, `max_min_transform.py`, `interpolation_transform.py`, `geofence_transform.py`, `nmea_checksum_transform.py`. — [logger/transforms/computed_fields_transform.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/computed_fields_transform.py)

Derived data pattern (true winds)
- `TrueWindsTransform(DerivedDataTransform)` takes course/speed/heading/rel-wind field names, `update_on_fields` (which arrivals trigger output) and `max_field_age` (refuse to compute on stale inputs); its docstring discusses the unsolved timestamp-alignment problem ("unless the vessel nav and anemometer values have identical timestamps, there's the question of how one integrates/interpolates/extrapolates values"). — [logger/transforms/true_winds_transform.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/transforms/true_winds_transform.py)
- The shipped true-winds logger template is a full logger: `readers: CachedDataReader` subscribing to the five input fields, `transforms: TrueWindsTransform`, `writers: CachedDataWriter` (plus an `on+influx` mode adding `InfluxDBWriter`), with `off`/`on` configs selectable by the logger manager. — [contrib/logger_templates/true_winds_logger_template.yaml](https://github.com/OceanDataTools/openrvdas/blob/master/contrib/logger_templates/true_winds_logger_template.yaml)

Cached data server
- `CachedDataServer` accepts DASRecords/dicts, keeps per-field in-memory history (default 86400 s back, `max_records` default 2880 per field), periodically backs up to a disk cache (`/var/tmp/openrvdas/disk_cache` in the example), and serves websocket clients with `fields`, `describe`, `subscribe` (with `seconds` and `back_records` back-fill), `ready`, and `publish` messages; it also exposes HTTP `GET /fields` and `GET /latest/<fields>`, with a caution that high-frequency HTTP polling delays websocket delivery. — [server/cached_data_server.py](https://github.com/OceanDataTools/openrvdas/blob/master/server/cached_data_server.py)
- `CachedDataReader(subscription, data_server='localhost:8766', bundle_seconds=0, return_das_record=False, ...)`; `bundle_seconds` aggregates N seconds of records into a list ("bundles by system clock time, and not by DASRecord timestamp"). — [logger/readers/cached_data_reader.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/readers/cached_data_reader.py)
- `CachedDataWriter(data_server, start_server=False, back_seconds=480, cleanup_interval=6, update_interval=1, ...)`. — [logger/writers/cached_data_writer.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/writers/cached_data_writer.py)

InfluxDB / Grafana
- `InfluxDBWriter(bucket_name, measurement_name=None, tags=None, auth_token, org, url, verify_ssl)` uses `influxdb_client` with the ASYNCHRONOUS write API; measurement defaults to the record's `data_id`; tags can be filtered per measurement. — [logger/writers/influxdb_writer.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/writers/influxdb_writer.py)
- `GrafanaLiveWriter` pushes InfluxDB line protocol to Grafana Live `/api/live/push`; its header notes "This code was created substantially via Google Gemini. The usual AI code disclaimers apply". — [logger/writers/grafana_live_writer.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/writers/grafana_live_writer.py)

YAML config and custom classes
- Each component is a dict with `class`, optional `module`, and `kwargs`. If `module` is present, `listen.py` does `importlib.import_module(module)` and `getattr(module, class_name)` (retrying after adding the OpenRVDAS root to the path); otherwise the class must already be in globals. So a custom transform can live in any importable package and be referenced as `class: MyQCTransform, module: local.qc.my_qc_transform`. — [logger/listener/listen.py](https://github.com/OceanDataTools/openrvdas/blob/master/logger/listener/listen.py) (lines ~141-200)
- Platform: Python 3.11+, installer supports macOS, Ubuntu 22.04+, Debian 12+ (incl. Raspberry Pi OS), Linux Mint 22+, RHEL/Rocky/Alma 9+; processes run under supervisord. — [INSTALL.md](https://github.com/OceanDataTools/openrvdas/blob/master/INSTALL.md)
- Project docs are a separate Jekyll site at oceandatatools.org/openrvdas-docs; auto-generated API docs live in `docs/html/`. — [docs/README.md](https://github.com/OceanDataTools/openrvdas/blob/master/docs/README.md)

Precedent for flags stored beside data (OOI)
- OOI stores QARTOD results in separate variables `<var>_qartod_results` (summary) and `<var>_qartod_executed` (per-test string, test names/order in metadata attributes); "QARTOD only Flags data, it does not remove data"; flag scheme 1 good, 2 not evaluated, 3 suspect, 4 fail, 9 missing. Thresholds come from existing OOI data and are published in the `qc-lookup` repo. — [OOI Launches QARTOD (Nov 2022)](https://oceanobservatories.org/2022/11/ooi-launches-qartod/)

### Inferences
- Do NOT put ML/QC inline in the raw-acquisition logger (serial reader -> logfile writer). `ValueFilterTransform` illustrates the hazard: it mutates the record and drops values, which violates "never overwrite raw". Any exception or latency spike in a transform in that path also stalls raw logging because transforms run serially inside `ComposedWriter.write()`.
- Best tier 1 (real time, ~1 Hz): a separate "QC logger" that copies the true-winds template: `CachedDataReader` (subscribe to N fields, optionally `bundle_seconds`) -> custom `QartodFlagTransform(DerivedDataTransform)` that emits new fields like `<var>_qc_flag` / `<var>_anomaly_score` plus a `qc_algorithm_version` field -> `CachedDataWriter` (so Grafana/displays show flags live) + `InfluxDBWriter` and/or a `LogfileWriter`/`DatabaseWriter` for a persistent flag stream. Raw logs remain untouched. Because it is a logger, it inherits logger-manager on/off modes and supervisord restarts for free.
- The custom class must hold per-variable rolling state (deque windows for spike/flat-line/rate-of-change, or river models) and protect it with a `threading.Lock` per the ComposedWriter thread-safety rule.
- Tier 2 (near real time, minutes): heavier methods (isolation forest over all variables, TSFM forecast residuals, cross-sensor consistency such as duplicate SST/TSG comparisons) run better as a standalone consumer (any process speaking the CDS websocket API, or an OpenRVDAS logger with `bundle_seconds` of 60 or more), publishing results back to the CDS via the `publish` message. This isolates heavy dependencies (onnxruntime, torch) from the core logger environment.
- Tier 3 (post hoc): change-point detection (ruptures), drift vs. reference (e.g. TSG vs. CTD casts, reanalysis matchups), and reprocessing with new algorithm versions run on stored logfiles/InfluxDB/NetCDF, producing versioned flag files. This is also where flags are written into CF/NetCDF ancillary variables for archive.
- `QCFilterTransform` returns a string message, so it is suitable for alerting (paired with `EmailWriter` or the logger-manager console), not for producing machine-readable flags.
- Issue #406 (a general value-matching transform) is the logical upstream place to propose a flag-emitting QARTOD transform; this researcher could not open the issue (GitHub API access was blocked in this session).

## Q2. Comparable stacks (CORIOLIX, Scripps MetAcq, NOAA SCS, R2R) and what QC/analytics they include

### Takeaway
None of the comparable shipboard stacks documents anything beyond range/delta checks and flagging infrastructure; the substantive automated QC in the US fleet happens shore side (SAMOS at FSU, R2R, NCEI's SCS Data Assembly Center). CORIOLIX is the notable trend: it was built for the RCRVs, includes ship/shore replication and "flagging", and NOAA is reported to be implementing it as the SCS successor.

### Cited Findings
- CORIOLIX (Oregon State): a web interface to "unlock the vessel data and provide shoreside access in near real-time"; services listed are Sensor Catalog, Data Acquisition Configuration, Data Processing, Local Data Access, Remote (shoreside) Data Access, and Quality Assurance; developed during RCRV construction, established as an ARF Specialized Service Pilot in 2023, first public release planned with delivery of RCRV Taani (July 2024); docs v1.2.1 (Nov 2023); code at github.com/R-DESC/CORIOLIX_app. — [CORIOLIX Documentation](https://hmsc-cms.dri.oregonstate.edu/docs/)
- CORIOLIX RVTEC 2022 slides: ship and shore metadata databases (Cruise, Vessel, Instrument, Event) synchronized bi-directionally; processing steps "Transformations, Derivations, Flagging, Binning"; "Data Replication: observational data created on ship and replicated to shore"; access via REST and ERDDAP; timing targets ~1 s and ~60 s for near-real-time steps; hosted on Point Sur and Endeavor (V1.0), Sikuliaq (metadata only), Taani, with clones planned for Narragansett Dawn and Mason. Specific QC tests are not named. — [UNOLS RVTEC 2022 CORIOLIX presentation](https://www.unols.org/sites/default/files/202211rvt_apXXIV.pdf)
- Scripps MetAcq: LabVIEW program by Shipboard Technical Support (SIO) that "acquires, filters, displays and distributes meteorological sensor data"; per-sensor averaging including wind vector averaging; QC limited to per-parameter `RANGE` and `UCR_RANGE` limits, a CHK MOD indicator listing non-responding sensors, an emulated-data status flag ('8'), and GPS failover; emails SAMOS reports directly. Manual rev 2.15, Aug 2019. — [MetAcq manual (copy on NOAA PSL ASTRAL 2023 Revelle)](https://downloads.psl.noaa.gov/psd3/cruises/ASTRAL_2023/Revelle/docs/MetAcq.pdf)
- NOAA SCS: first certified 1989 on NOAA Ship Malcolm Baldrige; Windows/.NET 4.8, IIS, SignalR/WCF, MySQL; recommended two-server setup (SCS-A app, SCS-B DB); QC "by monitoring I/O, applying delta and range checks, and plotting data after acquisition". — [SCS Overview](https://scsshore.noaa.gov/robohelp/Introduction/Overview.htm)
- NOAA Ship Data Assembly Center (NCEI/CISESS): SCS data automatically archived to NCEI since 2010; SCS NMEA converted to NetCDF; days-at-sea data received rose from as low as 66% (2016-2017) to 98-99% (2024-2025); non-zero-size files rose from ~83% average to 99% in 2025; the project "is paused while NOAA implements CORIOLIX, a successor to SCS". — [ESSIC: NOAA Ship Data Assembly Center: Ready for Deployment](https://essic.umd.edu/?p=27908)
- R2R + SAMOS: protocols for UNOLS operators to "transmit underway MET and TSG data to the SAMOS Data Center ... in near real-time" enabling "rapid QA, QC, and feedback on data quality during the cruise"; automated QC assigns a single alphabetic flag per value and "flags suspect values, rather than removing them"; checks include physical ranges, climatology, position over water, unrealistic speed; R2R QA includes file completeness, readability, expected variables. — [R2R real-time data page](https://www.rvdata.us/about/real-time-data)

### Inferences
- The gap that ML could fill is on-ship, during-cruise detection of the problem classes SAMOS analysts find manually 10 days later (see Q4). No comparable stack advertises statistical/ML anomaly detection.
- If NOAA moves to CORIOLIX, an algorithm packaged as a plain Python library operating on (timestamp, field, value) streams, with outputs as flag fields, is portable across OpenRVDAS, CORIOLIX and shore pipelines. Tying it to OpenRVDAS internals would limit reach.

## Q3. Edge compute constraints and cost/latency of candidate methods at 1 Hz x 50-200 variables

### Takeaway
At 1 Hz, rule-based QARTOD, online learners and a pre-trained isolation forest are computationally trivial on any ship server (well under 1 s per tick for 200 variables on one core, MEASURED HERE); naive repeated change-point detection is the only method that does not fit real time and belongs in batch. A ~1M-parameter forecaster like TTM is plausibly tens of milliseconds per forward pass for 200 channels on CPU (proxy estimate only, not measured on TTM). Compute is not the binding constraint; engineering (state, timestamp alignment, dependency isolation, model versioning) is.

### Cited Findings
Measured here (single thread unless noted; sandbox Xeon 2.1 GHz; script logic described so it can be reproduced):
- ioos_qc 3.1.1, four QARTOD tests (gross_range, spike, rate_of_change, flat_line) recomputed on a 600-sample window: 1.6 ms per variable per tick, so about 0.33 s per tick for 200 variables with naive full-window recomputation. MEASURED HERE.
- ruptures 1.1.10 PELT (l2, min_size 30, jump 5) on 3600 samples (1 h at 1 Hz): 1.5 s per variable, about 300 s for 200 variables; PELT on 1440 one-minute means (24 h): 0.46 s per variable. MEASURED HERE.
- scikit-learn 1.9.1 IsolationForest (100 trees), 200 features: fit on 20,000 rows 0.16 s; scoring one row 6.1 ms via sklearn; scoring a 3600-row batch 34 ms; same model exported with skl2onnx and run in ONNX Runtime 1.32 CPU: 1.3 ms per row; ONNX model size about 0.8 MB. MEASURED HERE.
- river 0.27.0 HalfSpaceTrees (10 trees, height 8, window 250) behind MinMaxScaler, one multivariate 200-feature record: 0.14 ms per score+learn; 200 separate univariate HST models: 18 ms per tick. MEASURED HERE.
- TTM proxy: a numpy dense MLP with ~1.1M parameters applied to 8 patches of 64 per channel (mimicking TTM-B context 512, patch 64) took 7.6 ms (50 channels) and 29 ms (200 channels) per forward pass single-threaded, 3 to 13 ms with 4 threads. This is NOT TTM; torch could not be installed and Hugging Face was blocked in this sandbox. MEASURED HERE as a FLOP-scale proxy only.
- TTM facts: "a compact model (starting from 1M parameters)"; TTM-B 1M params, context 512, patch 64; TTM-E 4M/1024; TTM-A 5M/1536; Moirai-S 14M, Moirai-B 91M, Moirai-L 311M, TimesFM 200M; "TTMs are lightweight and can be executed even on CPU-only machines"; pre-training channel-independent, with optional channel-mixing decoder for multivariate fine-tuning; pre-trained per forecast length. — [Ekambaram et al., TTM, arXiv 2401.03955v8 / NeurIPS 2024](https://arxiv.org/html/2401.03955v8)
- ioos_qc 3.1.1 released Nov 5, 2026; QARTOD tests include gross_range, climatology, spike, rate_of_change, flat_line, attenuated_signal, location, density_inversion, time_gap, etc., with stream (Numpy/Pandas/Xarray/NetCDF) and store (PandasStore, CFNetCDFStore) classes; docs do not describe a per-sample streaming mode. — [ioos_qc docs](https://ioos.github.io/ioos_qc); [PyPI ioos-qc](https://pypi.org/p/ioos-qc)
- river: library for online ML where models `learn_one`/`predict_one` one sample at a time, includes anomaly and drift detection families, and "focuses on clarity and user experience, more so than performance" while being "very fast at processing one sample at a time". — [river README](https://cdn.jsdelivr.net/gh/online-ml/river@main/README.md)
- skl2onnx lists IsolationForest, LocalOutlierFactor and OneClassSVM as supported converters. — [sklearn-onnx supported models](https://onnx.ai/sklearn-onnx/supported.html)
- TensorFlow Lite was renamed LiteRT on Sept 4, 2024; .tflite format unchanged; PyTorch models convert via ai-edge-torch; targets Android/iOS/embedded. — [Google Developers Blog](https://developers.googleblog.com/tensorflow-lite-is-now-litert/)
- Typical shipboard server stacks: NOAA SCS recommends two identical Windows servers (app + MySQL DB) — [SCS Overview](https://scsshore.noaa.gov/robohelp/Introduction/Overview.htm); OpenRVDAS supports generic Linux servers down to Raspberry Pi OS — [INSTALL.md](https://github.com/OceanDataTools/openrvdas/blob/master/INSTALL.md).

### Inferences
- Rule-based QC: implement QARTOD tests incrementally on rolling deques inside the transform rather than calling ioos_qc on full windows each tick; even the naive approach (0.33 s/tick for 200 vars) fits 1 Hz on one core, but incremental will be ~100x cheaper. Use ioos_qc as the reference implementation and for post-hoc batch so on-ship and shore flags are identical.
- Isolation forest / one-class models: train shore side on clean cruise data, ship as ONNX (sub-MB), score in ONNX Runtime at ~1 ms/row. Prefer scoring 1-min aggregates rather than raw 1 Hz to reduce false alarms from timestamp jitter across instruments.
- river is the natural fit for per-variable drift/anomaly that must adapt within a cruise without shore retraining; cost is negligible.
- ruptures: run PELT hourly or daily on 1-min means (0.46 s/var/day) as a batch job, or use an online change detector (e.g. river's drift detectors, CUSUM) in real time.
- TTM: forecasting residual-based anomaly (forecast next N minutes, flag large residuals) is computationally feasible at 1-min cadence on CPU for 200 channels; at 1 Hz with a 512-sample context the model would only see ~8.5 min of history, so downsampling to 1-min inputs (context 512 = ~8.5 h) is more meaningful. Feasibility is inferred, not measured on the real model.
- Ship server hardware is rarely the bottleneck; the real constraints are: not destabilising the acquisition host (run ML in a separate supervisord process or container with CPU limits), Python dependency weight (torch is hundreds of MB; ONNX Runtime is lighter), and operator trust.

### Gaps
- No published benchmarks found for ioos_qc throughput, river, or TTM CPU latency at shipboard scale; all latency numbers above are this researcher's sandbox measurements or proxies.
- No source found characterising "typical" UNOLS shipboard server specs (CPU/RAM); vendor and fleet hardware lists were not located.
- No precedent found for edge ML model deployment/MLOps at sea on research vessels (versioned model push, rollback); recommendations here are speculative.

## Q4. Starlink-era bandwidth, ship-to-shore patterns, shore-side services, and precedents for fleet-wide automated monitoring

### Takeaway
The UNOLS/ARF fleet moved to Starshield (Starlink) between May 2023 and Aug 2024, giving typically 100-250 Mbps down and 6-30 Mbps up with 5 TB/month plans, versus ~2 Mbps always-on from the retired Fleet Xpress. A full 1 Hz x 200-variable stream is a few kbps, so streaming everything ashore is now trivial; the edge/shore split should be driven by latency-to-action and resilience to outages, not bandwidth. Shore side becomes the home for fleet-wide cross-ship comparisons, reanalysis matchups and model training, which SAMOS already does at 1-min resolution with a 10-day lag.

### Cited Findings
- Starlink Maritime available July 2022; ARF pilot fall 2022; Starshield "Deployed fleet-wide May 2023 through August 2024 on ARF & USAP vessels"; advertised 350 Mbit/s best effort; typical 100-250 Mbps shore-to-ship and 6-30 Mbps ship-to-shore; plans "5TB per month or Unlimited", usage "occasionally pushing against 5TB/mo"; Fleet Xpress (GEO Ka) gave "2Mbps always on, and up to 10Mbps", Sealink ~20 Mbps, Iridium Certus 100-700 kbps but more reliable in extreme weather; cellular used in port "to avoid in-port use of Starlink/Starshield". — [HiSeasNet RVTEC 2024](https://unols.org/sites/default/files/2024-11/202410rvt_hsnrvtec.pdf)
- Nov 2025 update: Fleet Xpress/GX retired to fund Starshield (contracts cancelled 2025, service through July 2027); Gen 3 Starshield terminals replacing Gen 2 on Ocean/Global class in 2026 and Coastal/Regional in 2027; OneWeb pilot (Revelle terminal 100/20 Mbps, 5 TB; Endeavor terminal 30/6 Mbps moved to Armstrong Oct 2025); Iridium Certus kept as out-of-band path; Amazon Kuiper under NDA discussion. — [HiSeasNet update, RVTEC Nov 2025](https://www.unols.org/sites/default/files/2025-12/202511rvtec_lockwood_thomas_hiseasnet_update.pdf)
- SAMOS 2025: 30 of 31 recruited vessels reported; 6,611 ship days; 9,095,936 one-minute records; 260,659,626 measurements; 13,182,053 A-Y flags (~5.0%); preliminary files within minutes with automated QC only; research-quality visual QC on a 10-day delay for NOAA vessels and Falkor (too); 14 vessels automated QC only; SASSI statistical QC not active in 2025; vessels send "daily packages of one-minute interval SAMOS data" near 0000 UTC by email or are pulled from a shore-side service; common problems: flow distortion, thermal contamination (stack exhaust), RH > 100%, negative night shortwave, seawater flow restrictions/air intrusion, icing, birds, loose sensors; analysts email technicians at sea; report asks technicians to report suspected wind direction biases because analysts often cannot detect them. — [SAMOS 2025 Annual Data Quality Report](https://samos.coaps.fsu.edu/html/docs/2025SAMOSAnnualReport_final.pdf)
- SAMOS flag letters: e.g. B out of physical range, C time invalid, D fails T >= Tw >= Td, E fails true-wind recomputation, F unrealistic platform velocity, G > 4 sd from ICOADS climatology, H step, I interesting feature, J visual bad, K suspect, L over land, M known malfunction, N in port, S spike, T time duplicate, U/V/X/Y SASSI, Z good. — [SAMOS quality flags](https://samos.coaps.fsu.edu/html/samos_quality_flag.php)
- OOI: QARTOD implemented instrument by instrument starting with gross range and climatology, flags in separate `_qartod_results`/`_qartod_executed` variables, thresholds from historical data published in a lookup repo, some instruments "not well-suited towards QARTOD", and flag 3 "does not necessarily mean a data point is bad". — [OOI Launches QARTOD](https://oceanobservatories.org/2022/11/ooi-launches-qartod/)
- NOAA fleet: automated SCS archiving to NCEI since 2010, with completeness improving to 98-99% of days-at-sea in 2024-2025 after pipeline automation. — [ESSIC](https://essic.umd.edu/?p=27908)

### Inferences
- Bandwidth arithmetic (inferred): 200 variables x 1 Hz x ~16 bytes is ~3.2 kB/s (~26 kbps, ~0.28 GB/day uncompressed), under 0.5% of a 6 Mbps uplink and ~8 GB/month against a 5 TB plan. Streaming the full CDS/InfluxDB stream ashore continuously is cheap; the constraint is outages (weather, high latitude, Starshield policy changes), so edge-side buffering with store-and-forward replay (e.g. InfluxDB replication, MQTT with persistent sessions, or rsync of logfiles) is still required.
- Edge keeps: real-time flags that a technician acts on within minutes (flow-through pump stopped, sensor dropout, stack contamination wind sectors), and anything that must work during outages. Shore takes: fleet-wide comparisons (same-sensor-model behaviour across ships, cross-ship matchups when vessels are near each other), matchups to reanalysis (ERA5) and satellite SST/salinity, model training/retraining, and versioned reprocessing. Shore results can be pushed back down (5 TB down is ample) as updated ONNX models or threshold tables.
- SAMOS's 10-day visual QC lag and the fact that its statistical SASSI QC was off in 2025 suggest real value from earlier automated detection; SAMOS problem classes (flow distortion by relative wind sector, thermal contamination, RH saturation, seawater flow problems, wind direction bias) are concrete targets for edge detectors. Wind direction bias in particular is something analysts say they "often cannot detect", a candidate for shore-side multi-sensor/reanalysis comparison.
- Provenance pattern (from OOI + SAMOS + R2R): never remove data; store flags in separate variables per test with test name, parameters and algorithm version in metadata; in CF/NetCDF this maps to `ancillary_variables` with `flag_values`/`flag_meanings` (QARTOD 1/2/3/4/9) and can be served via ERDDAP. A crosswalk to SAMOS letters is needed for SAMOS submission.
